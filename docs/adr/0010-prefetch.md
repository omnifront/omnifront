# ADR-0010: prefetch

**وضعیت:** Accepted
**تاریخ:** 2026-11-09

## زمینه

رودمپ «prefetch» را در فهرست بعد از MVP داشت و فاصله‌ی مهاجرت از TanStack Query بود (`prefetchQuery`: داده را قبل از نیاز گرم می‌کند، داده‌ی تازه را دوباره نمی‌گیرد، و خطا را قورت می‌دهد). `fetchQuery` همیشه می‌گیرد و خطا را برمی‌گرداند، پس برای hover یا تغییر مسیر مناسب نیست. بودجه‌ی `query` پر است (ADR-0006، ADR-0008).

## تصمیم

1. تابع مستقل `prefetchQuery(client, options)` در ورودی جدا `@omnifront/query/prefetch`، نه متد `QueryClient`. کاربری که prefetch نمی‌کند بایتی نمی‌پردازد (مثل `hydration` و `structural`). بودجه‌ی ورودی: ۱KB.
2. رفتار: اگر داده در کش تازه است (جوان‌تر از `staleTime` و invalidate نشده) کاری نمی‌کند؛ به درخواست در جریان می‌پیوندد (dedupe)؛ **هرگز reject نمی‌شود** و خطا در کش می‌ماند. `staleTime` پیش‌فرض ۰ است، مثل TanStack.
3. گزینه‌های retry (`retry`، `retryDelay`) همان‌هایی‌اند که `fetchQuery` می‌گیرد.
4. برای آداپترها هوک جدا نمی‌سازیم: `prefetchQuery(useQueryClient(), ...)` کافی است و سطح API کوچک می‌ماند.

## گزینه‌های ردشده

- متد روی `QueryClient`: بودجه‌ی ۳KB را می‌شکست.
- `prefetchQuery` با `queryFn` اختیاری که از گزینه‌های ثبت‌شده بخواند: ثبت گزینه‌ها در client وجود ندارد و حالت پنهان اضافه می‌کرد.
- هوک `usePrefetch` در هر آداپتر: سه API مشابه برای یک تابع یک‌خطی.

## پیامدها (مثبت و منفی)

مثبت: مسیر مهاجرت از TanStack کامل‌تر؛ بدون هزینه برای بقیه.
منفی: ورودی جدا یعنی یک import بیشتر؛ `prefetchQuery` خطا را نشان نمی‌دهد، پس برای SSR که باید شکست را ببیند `fetchQuery` لازم است (در مستندات آمده).

## معیار بازبینی

اگر بودجه‌ی `query` بالا رفت یا prefetch وابسته به گزینه‌های ثبت‌شده شد (مثل `defaultOptions`)، ADR بازبینی شود.
